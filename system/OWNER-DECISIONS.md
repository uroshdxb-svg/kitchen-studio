# Private owner decisions — implementation and activation boundary

`/system/control/` supplies two independent controls after private authorization: **Approve** for the displayed task/action/exact target version, and **Go to chat** for a separately verified conversation reference. The public `/system/` dashboard and its JSON feed never contain these controls, private references or decision payloads. The owner page's static HTML is a sign-in shell; private records are loaded only through the authenticated API. Existing same-origin Supabase account sessions are reused. A signed-in customer is not thereby an approver.

## Current status

This PR prepares the UI, authenticated HTTP/RPC adapter and an **unapplied SQL proposal**. It does not deliver live worker continuation. The existing project has no private approval schema, designated approver ACL or verified receiving consumer. No deployment configuration, Supabase schema/role/permissions, credentials or automation was changed. Missing RPC/store returns503; an ordinary account returns403. The SQL file is outside the migration directory, never loaded by build or Worker. It must not be applied as a routine release step.

The proposal uses the existing Supabase project. The Worker validates the bearer token with `/auth/v1/user`, then calls narrow RPCs using that same user token. Server-owned ACL checks use `auth.uid()` plus an independently provisioned designated approver and allowed actions. Email, display name, profile and editable user metadata grant no authority. No service key is sent to the browser or added to this repository. See [Supabase getUser](https://supabase.com/docs/reference/javascript/auth-getuser) and [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Decision protocol

1. A trusted integration reads the authoritative current task, generation, action and exact artifact/head version. It creates an immutable private request with a short source freshness window, expiry, designated owner and verified conversation reference. The browser cannot submit or alter these bindings.
2. `GET /system/private/approvals` validates identity and private ACL and returns only designated requests. A verified chat link can remain available when the consumer is temporarily unavailable; Approve stays disabled. Missing private store never falls back to public queue data or guessed links.
3. `POST /system/private/approvals/<request UUID>/decision` requires same-origin JSON and a bearer token. Its body contains only `{version,idempotencyKey}`. The database locks the source/request, verifies current bindings and expiry, atomically inserts one immutable receipt and one outbox item, then marks approved. Stale requests return409. Repeated clicks and lost responses reuse the operation key. A different key cannot create a second receipt for a request.
4. The UI says **Approved — waiting for worker acknowledgement** after a durable receipt. A consumer reads the private receipt, independently rereads the authoritative current source, and continues through the existing execution route. For the current shared queue, an approval hold is retired by the supervisor with a referenced human decision, followed by a new bounded task/claim; retirement alone never executes work. Required CI, review, resource leases, publication QA and production checks still apply.
5. Only after the receiving worker accepts the exact continuation does the integration persist a separate immutable acknowledgement with worker and actual queue receipt references. The UI never creates an acknowledgement from an HTTP200, enabled schedule, test fixture or local button toggle.

Private responses use no-store, a strict output allowlist, bounded body reads and timeouts. Cross-origin writes, credential/query URL tricks, browser-supplied targets and unsafe conversation URLs are rejected. Authentication failures clear private UI records. Chat links allow only a verified exact HTTPS `chatgpt.com/c/<UUID>` address; absence or a malformed reference disables that button. No task-to-chat mapping has been invented.

## Explicit enabling decision needed

Before activation, obtain explicit user approval to create the proposed private schema and narrow RPC permissions, designate the actual owner's existing Supabase user ID and allowed action scope, and connect a trusted receipt/source-mirror/acknowledgement consumer through the existing execution route. Identify the real relevant private conversation reference separately. The proposal creates no user, consumer role, secret, grant of approver status or enabled runtime. If the consumer requires new credentials or permissions, stop that enabling step for approval; never borrow another task's credentials.

Review SQL against the target Postgres version before applying it through the project's normal migration process. Exercise authorization and atomicity against real Postgres in an approved isolated environment, including concurrent different keys, source updates during lock waits, revoked owner, changed head/generation, expiry and lost responses. Verify real queue acceptance/continuation and immutable ACK readback before enabling production Approve. Expired consumer proof must disable decisions. Verify real signed-out/customer/owner states, both buttons, mobile/desktop and failure recovery on the exact deployed preview before proposing a release.

## Evidence limits

`approval-endpoint.test.mjs` uses an injected fake auth/RPC service. It verifies HTTP validation and fail-closed response contracts; it does not execute SQL or prove database concurrency. `control-browser-check.mjs` labels its screenshots **ISOLATED TEST**, stubs authentication and private API, and reports `liveApprovalVerified:false`. It verifies separate buttons, response-loss retry, stale/error handling, safe links, acknowledgement presentation and320/390/1440px layouts. Normal dashboard/browser/MCP/discovery/queue regressions still run in hosted CI. Passing fixtures, a successful Cloudflare preview or an unapplied proposal must never be reported as live approval or real agent continuation.
