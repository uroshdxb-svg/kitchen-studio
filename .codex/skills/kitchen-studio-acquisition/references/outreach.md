# Outreach and validation

## Product boundaries

Use the current playbook as authority. Describe laying out real kitchen equipment and preparing a concept for supplier review only when the available build supports those actions. Do not promise engineering, approvals, supplier acceptance, live MCP reliability or quantified savings without evidence.

Keep a small café/QSR operator as the primary recruit. Suppliers, consultants and architects can contribute review evidence without being counted as primary operators.

## Draft pattern

Subject: A short project-specific topic

Hi [company] team,

[One factual observation from their official page.] I'm recruiting [current pilot terms] to try Kitchen Studio using a real room and equipment requirements. [One question establishing whether a relevant decision remains open.]

[Verified sender signature]

Use the team greeting unless a public source confirms the person's role. Reference the project plainly, avoiding an implied existing relationship. Include any footer required by the actual sending setup and user-approved policy before showing the exact batch for release.

## Qualification

Ask these across a short conversation:

- Is the kitchen/refit active within six months, and are layout/equipment choices still open?
- Is a usable floor plan or measured room available?
- Can the participant influence equipment decisions or bring the responsible operator?

Offer the current pilot format after confirming fit. Check real availability before proposing dates. Keep private plans out of source code.

## Reply classification

| Kind | Next action |
|---|---|
| `interested` | Confirm gaps and draft the next step |
| `question` | Answer from verified facts; disclose unknowns |
| `later` | Pause; record timing only if supplied |
| `declined` | Close the lead and stop pending outreach |
| `opt_out` | Suppress address/domain; no marketing reply |
| `bounce` | Suppress address; do not guess another email |

Record replies once using the provider message ID. A positive reply is not qualified demand until the three checks are confirmed. A free trial is not a purchase. Record payments only with evidence, currency and amount.

## Example run requests

- “Find 10 more public prospects and prepare five messages.” Run scout/draft and return a packet.
- “Send the five messages in this reviewed packet from my verified mailbox.” Record authorization, then reserve/save/send/receipt for each.
- “Process these replies.” Classify/suppress/qualify and prepare responses. Send only when specifically authorized.
- “What did we validate?” Summarize actual outcomes, separating free and paid evidence.
